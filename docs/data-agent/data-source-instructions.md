# SMO Analytics SQL guidance

This Lakehouse is the authoritative SQL consumption layer for SMO Analytics.

Use only the selected business tables. Do not use legacy/raw `smopt` tables for
user-facing analysis.

Business schemas:

- `semantic_model_metadata`
- `analysis_control`
- `semantic_model_optimization`
- `semantic_model_best_practice`
- `semantic_model_vertipaq`

# Table routing

Use `semantic_model_metadata.semantic_models` for the current semantic-model inventory,
workspace/model identity, latest analysis status, latest analysis timestamp, model size,
storage mode, and scanner version.

Use `analysis_control.semantic_model_analysis_runs` for historical scan executions,
failures, partial runs, permission checks, component status, duration, and error details.

Use `semantic_model_optimization.semantic_model_optimization_overview` for the current
high-level optimization status of each semantic model.

Use `semantic_model_optimization.semantic_model_optimization_opportunities` for
optimization areas, opportunity priority, opportunity actionability, and summarized
optimization issues.

Use `semantic_model_optimization.semantic_model_optimization_recommendations` for
specific remediation actions, recommendation priority, change risk, validation,
rollback, automation eligibility, and why the action matters.

Use `semantic_model_optimization.semantic_model_optimization_findings` for detailed
technical evidence, affected objects, rules, severity, confidence, suppression reasons,
and finding-level priority.

Use `semantic_model_best_practice.semantic_model_best_practice_rule_findings` only for
Best Practice Analyzer / BPA-specific questions.

Use `semantic_model_vertipaq.semantic_model_table_storage` for table-level VertiPaq
storage analysis.

Use `semantic_model_vertipaq.semantic_model_column_storage` for column-level VertiPaq
storage analysis.

# Current state versus scan history

Current optimization state and historical scan execution are different concepts.

For questions such as:
"current optimization status", "current issues", "current recommendations",
"current findings", or "latest optimization result":

prefer the current-state business tables.

For questions such as:
"latest scan execution", "scan history", "failed scans", "previous scans",
"scan duration", or "why did the scan fail":

use `analysis_control.semantic_model_analysis_runs`.

When identifying the latest historical run for each semantic model, partition by
`semantic_model_id` and order by `COALESCE(completed_at, started_at)` descending.

A failed latest scan can coexist with an older usable current optimization state.
Never present preserved current-state results as if they were generated by a failed
latest execution.

# Semantic model scope

Use `semantic_model_id` for reliable filtering and joins.

Prefer `semantic_model_name` and `workspace_name` in user-facing output.

When the user says:
"all semantic models", "all current models", "the available models", "the five models",
or similar wording without explicitly naming them, determine the current scope from
`semantic_model_metadata.semantic_models`.

Never reconstruct the current model list from previous conversation history, examples,
or remembered model names.

A previously mentioned model must not be included unless it exists in the current
`semantic_models` table.

When possible, scope multi-table queries using `semantic_model_id` rather than a
hard-coded list of semantic model names.

# Relationships and joins

Always keep multi-table queries scoped to the same semantic model.

Prefer IDs and explicit relationship keys instead of names.

For historical analysis:

`semantic_models.semantic_model_id`
joins to
`semantic_model_analysis_runs.semantic_model_id`.

When joining current overview to analysis history, never join on `analysis_id` alone.

Use at minimum:

`overview.analysis_id = analysis_runs.analysis_id`
AND
`overview.semantic_model_id = analysis_runs.semantic_model_id`.

For optimization hierarchy, use `semantic_model_id` plus the relevant optimization
relationship key.

Opportunities can relate to recommendations and findings through `opportunity_id`,
but `opportunity_id` represents a broad optimization opportunity and is NOT sufficient
to prove that one specific recommendation is supported by one specific finding.

# Recommendation-to-finding evidence mapping

Never join a specific recommendation to findings using only:

`semantic_model_id + opportunity_id`.

That can create false many-to-many relationships.

For specific recommendation-to-finding evidence, prefer:

`recommendations.semantic_model_id = findings.semantic_model_id`
AND
`recommendations.analysis_id = findings.analysis_id`
AND
`recommendations.analysis_scope_key = findings.analysis_scope_key`
AND
`recommendations.issue_scope_key = findings.issue_scope_key`
AND
`recommendations.opportunity_id = findings.opportunity_id`.

If an exact recommendation-to-finding relationship cannot be established, describe
the findings as evidence for the broader opportunity instead of claiming that they
specifically support the individual recommendation.

Avoid joins that multiply fact rows.

When counting entities after joins, use `COUNT(DISTINCT ...)` where necessary.

# Actionability semantics

Actionability is an entity-level property.

Valid states are:

- `ACTIONABLE`
- `REVIEW_REQUIRED`
- `INFORMATIONAL`
- `SUPPRESSED`

When the user asks for recommendations requiring human review, filter strictly on:

`semantic_model_optimization_recommendations.actionability_status = 'REVIEW_REQUIRED'`.

Do not include a recommendation merely because its parent opportunity is
`REVIEW_REQUIRED`.

For actionable recommendations, filter recommendation actionability directly.

For suppressed findings, filter:

`semantic_model_optimization_findings.actionability_status = 'SUPPRESSED'`.

A parent opportunity's actionability does not override the stored actionability of an
individual recommendation or finding.

Do not recommend implementing suppressed findings.

Do not describe REVIEW_REQUIRED items as automatically safe to implement.

# Priority semantics

Use the stored deterministic priority values.

Priority bands are:

- `P1_CRITICAL`
- `P2_HIGH`
- `P3_MEDIUM`
- `P4_LOW`

For opportunities use `priority_score`.

For recommendations use `recommendation_priority_score`.

For findings use `finding_priority_score`.

Do not rank entities only by finding count, severity, or estimated saving when a stored
priority score is available.

# Cross-model comparison

SMO Analytics does NOT currently provide a single model-level optimization score,
health score, quality score, or maturity score.

Do not convert `MAX(priority_score)`, `AVG(priority_score)`, finding counts, or other
aggregations into an "overall optimization score".

`priority_score` belongs to an opportunity.
`recommendation_priority_score` belongs to a recommendation.
`finding_priority_score` belongs to a finding.

When comparing semantic models, prefer fields from
`semantic_model_optimization.semantic_model_optimization_overview`, such as:

semantic model size, opportunity count, recommendation count, actionable recommendation
count, review-required recommendation count, finding count, high-severity finding count,
suppressed finding count, analysis status, and component availability.

If `MAX(priority_score)` is shown, label it explicitly as the
"highest opportunity priority score", not as an overall model score.

Keep compared semantic models as separate rows/groups unless the user explicitly asks
for aggregation.

# Data availability

Do not confuse:

analysis not run,
analysis not applicable,
analysis completed successfully with zero findings,
and analysis data unavailable because of an error.

Use component status fields and `data_availability_explanation` where available.

A zero result must not automatically be interpreted as missing data.

If evidence is unavailable, state that instead of inferring a value.

# VertiPaq semantics

For storage ranking, use actual storage-size fields such as `total_size_bytes`.

Do not rank columns primarily by cardinality unless the user explicitly asks for
cardinality.

Do not treat a large table or column as proof of poor model design.
Combine storage evidence with optimization findings when deciding whether it should be
optimized.

# Estimated savings

`estimated_saving_bytes_low` and `estimated_saving_bytes_high` are directional storage
estimates only.

Do not describe them as validated:

Capacity Unit savings,
refresh-time improvement,
query-performance improvement,
or financial savings.

Validated CU/performance benefit requires controlled before-and-after measurement.

# SQL generation rules

Use fully qualified schema and table names.

Filter early when the user specifies a semantic model or workspace.

Prefer exact semantic-model-name matching when possible.

If no exact model exists, say so rather than returning a different model.

For "top N" requests, explicitly ORDER BY the correct priority or size field before
applying TOP.

When information already exists in one business table, avoid unnecessary joins.

Return only columns needed to answer the question and avoid exposing internal IDs unless
needed for troubleshooting or disambiguation.
